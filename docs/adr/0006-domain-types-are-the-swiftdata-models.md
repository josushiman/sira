# The domain types are the SwiftData models

Matches must survive the app closing, which means `Match`, `Round` and `Entrant` have to be stored. We decided that these domain types *become* the persistence types — `@Model` classes, with no parallel set of persistence records and no mapping layer — so that there is one description of a Match in the codebase. The alternative, keeping the value types and mapping them to and from separate storage records, was rejected because it means maintaining two descriptions of a domain that changed in three consecutive commits, and a mapping layer only drifts in the direction of the description nobody is testing.

The cost is accepted deliberately: these types stop being value types. `Match.undoLastRound()` becomes removing the Round from the relationship and deleting the object rather than a `removeLast()` on an array of structs; `MatchStore.binding(for:)` disappears entirely, taking its missing-id `fatalError` with it — a reference type needs no `Binding` to be mutated in place, and that crash was only ever safe while no Match could be deleted; previews and view tests need a container rather than a bare array of fixtures. The risk this introduces is bounded by the shape of this domain in particular: Rounds are append-only, the only removal permitted is the last Round, and the Engines stay pure functions that read a Match's properties without mutating it.

A Round's `deltas`, `cifteCallers`, `losingEntrantID`, `okeyAtanID`, `gostergeFinderID` and its `RejoinEvent`s stay inline attributes on the Round rather than becoming relationships. Per ADR 0005 the Engines read a whole Round and derive from it; nothing queries into these fields, so modelling them as relationships would buy query power that is never used and cost a join and a lifecycle to manage. The known consequence is that a UUID-keyed dictionary gets no referential integrity from SwiftData — a removed Entrant would orphan its keys — which is safe only while Entrants cannot be removed from a Match. Entrants are a relationship owned by their Match and cascade-deleted with it, and keeping removal impossible is a constraint this decision depends on.

Storage is local-only: no CloudKit, no account, no network. This is a one-way door worth knowing about before someone reaches for sync, because adopting CloudKit later would require unique constraints to be dropped and stored properties to become optional or defaulted throughout the schema.
